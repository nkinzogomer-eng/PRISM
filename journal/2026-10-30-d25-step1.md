# 2026-10-30 — D2.5 Stage 1: target validation

**Decision:** Alchemy Modular Account `v2.0.0`
(`bd75c9eca7ff5a66aaebc3cf2dab43ddc4622482`) is accepted as the D2.5 domain
target. Rhinestone is not adopted as a replacement.

## Why this was necessary

D2.5 needs a real modular smart-account codebase as a laboratory, not another
synthetic generator. Before designing anything, the candidate had to be shown to
be *usable*: exact commit, pinned compiler, locked dependencies, clean build,
passing reference suite, and no interference with the SCM track.

## What was actually done

* Cloned the repository and checked out the requested commit; it is exactly the
  `v2.0.0` tag, tree `30281664…`.
* Pinned forge 1.7.1 (npm), pnpm 9.15.0 (npm) and a native, SHA-256-verified
  solc 0.8.26 from `ethereum/solc-bin`.
* Locked dependencies with `pnpm install --frozen-lockfile` (469 packages) and
  recursive submodules at their pinned commits.
* Clean build: 228 files, 31.72 s, 0 errors, 0 warnings; two independent clean
  builds produced byte-identical artifact sets (232 artifacts).
* Reference suite: 292 tests in 46 suites, all passing, twice (default fuzz seed
  and `FOUNDRY_FUZZ_SEED=20261030`).
* PRISM baseline unchanged: 53 tests, `OK (expected failures=1)`.

## What was not done

No source modification, no new mechanism, no chain interaction, no RPC, no key
material, no fork mode. The target stays outside the repository.

## Findings worth remembering

1. The target's own CI pins nothing but solc (`foundry-toolchain@v1` with
   `version: nightly`). Any later D2.5 stage must cite *our* toolchain, not "the
   target's CI".
2. The target's submodule graph is cyclic (`light-account` ↔ `modular-account`);
   recursive updates need a second pass and produce nested duplicates by design.
3. Foundry 1.7.1's new linter turns the target's `deny_warnings = true` into a
   failing lint gate on the `optimized-build` profile. Compilation itself
   succeeds; `-D never` isolates the diagnostic gate without changing settings.
4. The Emscripten `solcjs` build aborts with a wasm `memory access out of bounds`
   on this target's full payload (~136+ sources). Do not build D2.5 tooling on
   `solcjs`; use the native binary.

## Consequences for Stage 2

Stage 2 (mechanism design) may proceed against this target, but:

* every measured claim must be compared against the 292-test reference suite as a
  baseline, never presented as one;
* the Stage 1 environment lock (`reports/d25-step1/environment.lock.json`) and
  artifact manifest are the reproducibility anchors;
* D2.5 is not PRISM Phase 4 and performs no offensive or defensive security
  testing; the phase register is unchanged.
